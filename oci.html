What you're actually shipping

This repo builds down to one runnable jar: the app module pulls in every other module (common, duffle-api, search-service, search-ai, notification, payment-service, booking-service) and the React SPA in frontend is built by Vite straight into app/src/main/resources/static, so the jar serves API and UI from one origin on port 8090. There's no existing Dockerfile or docker-compose.yml in the repo yet — this guide has you write both.

At runtime the app needs, all reachable from wherever it runs:

DependencyUsed byHas a default?
PostgreSQLEvery module (shared travel DB, Flyway-migrated)No — hardcoded to localhost:5434
ElasticsearchAirport / flight searchYes, localhost:9200
RedisCaching, payment-serviceYes, localhost:6379
KafkaBooking → payment → notification outbox eventsYes, localhost:9092
SMTP servernotificationYes, localhost:1025

Plus three third-party API integrations that have no defaults and will stop the app from starting if they're missing:

  • MISTRAL_API_KEY — search-ai's Spring AI chat model
  • DUFFEL_API_KEY — flight search & booking via Duffel
  • RAZOR_PAY_API_KEY, RAZOR_PAY_API_SECRET, RAZORPAY_WEBHOOK_SECRET — payment-service via Razorpay

The plan: one Ampere A1 compute instance (Always Free gives you up to 4 OCPU / 24GB RAM of it — comfortably enough for the app plus every one of those services in containers on the same box), fronted by Caddy for free TLS.

01

Create the Always Free account

Everything downstream depends on which home region you pick here — it can't be changed later.

  1. Go to Oracle's cloud free tier sign-up page and start registration with your email.
  2. Verify your email, then your phone number by SMS code.
  3. Enter a credit or debit card for identity verification. This does not create a recurring charge — Oracle explicitly does not auto-upgrade you to a paid account, and Always Free resources stay free indefinitely.
  4. Choose your Home Region carefully.
    Region matters more than it looks. Ampere A1 "out of host capacity" errors are a known Always Free pain point in some regions. If you already know a specific region has been reliable for A1 capacity, prefer it; otherwise pick the region physically closest to your users and be ready to retry the instance launch a few times in Phase 4.
  5. Submit and wait for the "your account is ready" email — provisioning usually takes a few minutes, occasionally longer.
02

Set a safety net before you provision anything

A new account starts in a 30-day/$300 trial layered on top of the permanent Always Free allowance. It's easy to accidentally pick a shape or option that isn't Always Free eligible — a budget alert catches that before it becomes a bill.

  1. In the console, open Governance & Administration → Budgets → Create Budget.
  2. Scope it to your whole tenancy, set an amount like $1, and add an alert rule at a low threshold (e.g. actual spend > $0.01).
  3. Add your email as the alert recipient.

Two ground rules that keep you inside Always Free for this deployment:

  • Only choose shapes and images explicitly labeled "Always Free eligible" in the console.
  • Skip Autonomous Database entirely — it's Oracle DB, not Postgres, and would mean rewriting the JDBC layer. This guide runs Postgres in a container instead, which is zero code changes and still free (self-hosted on the free compute + block storage allowance).
03

Open the network before you need it

Doing this before launching the instance means you're not debugging "why can't I reach my server" and "did I configure Docker right" at the same time.

  1. Go to Networking → Virtual Cloud Networks. A default VCN was created for you when the account provisioned — use it.
  2. Open its public subnet's Default Security List → Ingress Rules.
  3. Confirm/add these stateful ingress rules for 0.0.0.0/0:
    PortProtocolWhy
    22TCPSSH (usually already present)
    80TCPHTTP — Let's Encrypt validation + redirect
    443TCPHTTPS — the actual front door
  4. Deliberately don't open 8090 here — the app port stays internal, reached only through the reverse proxy you'll set up in Phase 10.
  5. Optional but recommended: Networking → IP Management → Reserved Public IPs → Create Reserved Public IP. One is included in Always Free, and it keeps your address stable if you ever stop/start the instance.
04

Launch the Ampere A1 instance

This one VM is the entire deployment target — app container plus every backing service, all on the free 4 OCPU / 24GB Arm allowance.

  1. Generate an SSH key pair locally if you don't already have one: ssh-keygen -t ed25519 -C "travel-ai-oci".
  2. Compute → Instances → Create Instance.
  3. Name it, e.g. travel-ai.
  4. Under Image and shape, pick a Canonical Ubuntu 24.04 image (marked "Always Free eligible"), then change the shape to Ampere · VM.Standard.A1.Flex and set it to 4 OCPU / 24 GB memory — the full free allotment.
  5. Attach it to the public subnet from Phase 3, with a public IP assigned (your reserved IP, if you made one).
  6. Upload the .pub half of the key pair you generated.
  7. Leave the boot volume at its default (you can grow it later, up to 200GB total across all volumes, still free).
  8. Create. Provisioning takes one to a few minutes.
"Out of host capacity" on the A1 shape? This is the most common Always Free snag — it means that region's free Arm pool is momentarily full, not that your account is blocked. Wait a bit and retry, try a different Availability Domain in the same region if more than one is offered, or try again at an off-peak hour. It almost always succeeds within a day of retries.
05

Prepare the box

Oracle's Ubuntu image ships with its own iptables rules that drop everything except SSH, on top of the cloud-level Security List you already opened. Both layers need to agree.

local machine
ssh -i ~/.ssh/id_ed25519 ubuntu@<your-instance-public-ip>

Update and patch

sudo apt update && sudo apt full-upgrade -y

Open 80/443 in the host firewall

Check the existing chain first so you insert before the final reject rule, not after it:

sudo iptables -L INPUT -n --line-numbers

Then insert accept rules ahead of that reject line (adjust the line number to match what you saw):

sudo iptables -I INPUT 5 -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -p tcp --dport 443 -j ACCEPT
sudo apt install -y iptables-persistent
sudo netfilter-persistent save

Notice port 8090 is intentionally never added here — that keeps the raw app port unreachable from the internet even though Docker will bind it on the host.

Let Elasticsearch actually start

Elasticsearch refuses to boot on Linux without this kernel setting:

echo "vm.max_map_count=262144" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

Install Docker

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker
sudo systemctl enable --now docker

Docker's official install script builds the right (arm64) images for this VM automatically — nothing else to configure for architecture.

06

Pull the code down

Building on the VM itself (Arm) avoids any cross-architecture image weirdness — the same Dockerfile just works because it's compiled where it runs.

sudo apt install -y git
git clone https://github.com/<your-org>/travel-ai.git
cd travel-ai

If the repo is private, clone with a personal access token in the URL, or copy a tarball up with scp instead.

07

Containerize it

Nothing in the repo builds a container image yet. The build only needs a JDK — the checked-in mvnw wrapper fetches Maven itself, and the frontend module's frontend-maven-plugin fetches its own pinned Node/npm and runs the Vite build, which writes straight into app/src/main/resources/static. A full, unfiltered reactor build (no -pl) is what guarantees the frontend module builds before app packages its resources.

Dockerfile (repo root)

Dockerfile
FROM eclipse-temurin:25-jdk AS build
WORKDIR /workspace
COPY . .
RUN chmod +x mvnw && ./mvnw -B -DskipTests package

FROM eclipse-temurin:25-jre
WORKDIR /app
COPY --from=build /workspace/app/target/app-*.jar ./app.jar
EXPOSE 8090
ENTRYPOINT ["java", "-jar", "app.jar"]

.dockerignore (repo root)

The frontend/node_modules tree alone is large enough to make an unfiltered build context painfully slow to send to the Docker daemon — exclude it.

.dockerignore
.git
.idea
**/target
**/node_modules
*.log
.env
Expect the first build to take a while. It's compiling eight Maven modules and a full npm install + Vite build in one pass. On a 4 OCPU A1 instance this typically finishes in a few minutes — let it run rather than assuming it's stuck.
08

Compose the stack

This is where every backing service and every secret the app needs gets wired together in one file, entirely inside the one VM.

Secrets first — .env (repo root, already gitignored)

.env
POSTGRES_PASSWORD=choose-a-strong-password
MISTRAL_API_KEY=your-mistral-key
DUFFEL_API_KEY=your-duffel-key
RAZOR_PAY_API_KEY=your-razorpay-key
RAZOR_PAY_API_SECRET=your-razorpay-secret
RAZORPAY_WEBHOOK_SECRET=your-razorpay-webhook-secret
Lock it down: chmod 600 .env. It already matches an existing .gitignore entry in this repo, so it won't get committed by accident.

docker-compose.yml (repo root)

Note the app service overrides SPRING_DATASOURCE_URL — the checked-in application.yaml hardcodes jdbc:postgresql://localhost:5434/travel, which only makes sense for local dev. Spring Boot's relaxed binding lets an environment variable override it without touching a single line of code.

docker-compose.yml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: travel
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    restart: unless-stopped

  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.15.3
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
      - "ES_JAVA_OPTS=-Xms1g -Xmx1g"
    volumes:
      - es_data:/usr/share/elasticsearch/data
    restart: unless-stopped

  kafka:
    image: bitnami/kafka:3.8
    environment:
      - KAFKA_CFG_NODE_ID=0
      - KAFKA_CFG_PROCESS_ROLES=controller,broker
      - KAFKA_CFG_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093
      - KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://kafka:9092
      - KAFKA_CFG_CONTROLLER_QUORUM_VOTERS=0@kafka:9093
      - KAFKA_CFG_CONTROLLER_LISTENER_NAMES=CONTROLLER
      - KAFKA_CFG_LISTENER_SECURITY_PROTOCOL_MAP=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      - ALLOW_PLAINTEXT_LISTENER=yes
    volumes:
      - kafka_data:/bitnami/kafka
    restart: unless-stopped

  mailpit:
    image: axllent/mailpit:latest
    restart: unless-stopped

  app:
    build: .
    depends_on:
      - postgres
      - redis
      - elasticsearch
      - kafka
      - mailpit
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/travel
      SPRING_DATASOURCE_USERNAME: postgres
      SPRING_DATASOURCE_PASSWORD: ${POSTGRES_PASSWORD}
      ELASTICSEARCH_URIS: http://elasticsearch:9200
      REDIS_HOST: redis
      REDIS_PORT: 6379
      KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      MAIL_HOST: mailpit
      MAIL_PORT: 1025
      MISTRAL_API_KEY: ${MISTRAL_API_KEY}
      DUFFEL_API_KEY: ${DUFFEL_API_KEY}
      RAZOR_PAY_API_KEY: ${RAZOR_PAY_API_KEY}
      RAZOR_PAY_API_SECRET: ${RAZOR_PAY_API_SECRET}
      RAZORPAY_WEBHOOK_SECRET: ${RAZORPAY_WEBHOOK_SECRET}
    ports:
      - "127.0.0.1:8090:8090"
    restart: unless-stopped

volumes:
  postgres_data:
  es_data:
  kafka_data:

Binding the app's port as 127.0.0.1:8090:8090 rather than just 8090:8090 means Docker itself only exposes it to the loopback interface — the reverse proxy in Phase 10 reaches it locally, nothing else can.

No real email delivery here. Mailpit only captures mail for inspection (web UI on port 8025, tunnel it over SSH if you want to look) — it doesn't deliver anything. If notification emails need to actually reach inboxes, swap MAIL_HOST/MAIL_PORT for a real SMTP relay (OCI Email Delivery, or any provider's SMTP credentials) instead of the mailpit service.
09

First boot

This is the moment every Flyway migration across booking-service, payment-service, notification, and duffle-api/flight runs against the same shared schema for the first time outside your laptop.

docker compose up -d --build
watch the app come up
docker compose logs -f app

Look for Flyway's migration log lines followed by Started AppApplication. Then confirm from the box itself:

curl -s http://localhost:8090/actuator/health

A {"status":"UP"} response means Postgres, Redis, Elasticsearch, and Kafka are all reachable and the app is healthy.

10

Put a real front door on it

Port 8090 is only bound to loopback now, and it's HTTP, not HTTPS. Caddy gets you both a public URL and free automatic TLS in about four lines of config.

  1. Decide on a hostname. If you own a domain, point an A record at the instance's public IP. If not, use a free wildcard-DNS-to-IP service like sslip.io — e.g. 203-0-113-10.sslip.io resolves straight to 203.0.113.10, and Let's Encrypt can issue a real certificate for it because it's a genuine public DNS name.
  2. Install Caddy:
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy
/etc/caddy/Caddyfile
your-hostname-or-sslip-address {
    reverse_proxy localhost:8090
}
sudo systemctl reload caddy

Caddy requests and renews the certificate itself the first time it sees a request on 443 — nothing else to run.

11

Make it survive a reboot

A patch, a resize, or a stop/start shouldn't mean SSH-ing back in to manually bring the stack up.

  • Every service in the compose file already has restart: unless-stopped — Docker remembers a container's desired state across a daemon restart and brings it back on its own.
  • The only other requirement is that the Docker daemon itself starts on boot, which the install script in Phase 5 already enabled: sudo systemctl enable --now docker.
  • Caddy is a systemd service too and is enabled by its own package install.

Worth actually testing once:

sudo reboot

Wait a minute, reconnect over SSH, and re-run the curl .../actuator/health check from Phase 9.

12

Guardrails and teardown

"Free forever" from Oracle still has two catches worth knowing before you walk away from this for a month.

  • Idle-account reclamation. Oracle can reclaim Always Free resources after a sustained stretch with no console sign-in and no resource activity — check the current threshold in OCI's billing documentation, since policy details do shift. Logging into the console occasionally is enough to keep the account counted as active.
  • Stay inside the free shapes. The budget alert from Phase 2 is your tripwire if a future resize or a second instance accidentally steps outside the Always Free allotment.

What "done" looks like

  • ✓ Always Free tenancy created, home region chosen deliberately
  • ✓ Budget alert active
  • ✓ One Ampere A1 instance (4 OCPU / 24GB), Security List open on 22/80/443 only
  • ✓ Docker + the full stack running via docker compose, app port bound to loopback only
  • ✓ Caddy serving the app over HTTPS on a real hostname
  • ✓ Stack confirmed to survive a reboot

If you ever want it gone

docker compose down -v

Then in the console: Compute → Instances → terminate the instance (tick "permanently delete the attached boot volume"), and if you reserved one, release the Reserved Public IP so it doesn't sit unused.
